# ADR-003: Make Task the aggregate root with one TaskRepository

**Date:** 2026-10-11
**Status:** accepted

## Context

The original design listed a repository per entity (`TaskRepository`,
`VerificationRepository`, `ArtifactRepository`). But checks, artifact
versions, approvals, and audit entries only make sense inside one task, and the
rules span them: a new artifact resets every check, a failed check clears
approvals, and approval needs all six checks. If services could load and save
these parts separately, a rule could be skipped or half applied.

## Decision

`Task` is the aggregate root and the only way to change its checks, artifacts,
approvals, and audit history. The Data tier has one `TaskRepository` interface
that saves and loads whole tasks. Every service depends only on
`TaskRepository`: it loads the task, calls a `Task` method, and saves the task.

## Alternatives considered

**One repository per entity.** Allows smaller queries, such as loading one
check, but lets callers change parts of a task without going through its rules.

## Consequences

Each rule is enforced in one place and each change is saved as a unit, which
keeps the rules simple to test. Loading a task always loads all its parts,
which is fine at this project's size. The JPA version in #59 must store and
rebuild the whole aggregate without re-running rules or adding audit entries.
I would revisit this if tasks grew large enough that loading them whole became
slow.
