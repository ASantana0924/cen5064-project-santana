# ADR-005: Developer identity is supplied by the client, with no authentication

**Date:** 2026-10-12
**Status:** accepted

## Context

The rules depend on who acts: the owner of a task, the reviewer of a check,
and two different approvers. Real login (accounts, passwords, sessions or
tokens) would take weeks and is not what this course project is about. The
audit history still needs a name on every action.

## Decision

Every action request to the REST API carries a `developer` field (a query
parameter on DELETE), and the Domain records that name. The frontend keeps the
chosen name in an "Acting as" picker saved in the browser. There is no
authentication and no user table.

## Consequences

Any client can act as anyone, so the two-approver rule and the audit history
are only as honest as the people using the app. That is acceptable for a
single-team demo but not for real use. Adding Spring Security later would
replace the `developer` field with the logged-in user in the Presentation tier;
the Domain and Service tiers would not change.
