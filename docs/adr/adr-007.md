# ADR-007: Map the Task aggregate to JPA entities in the Data tier and rebuild it with restore factories

**Date:** 2026-11-16
**Status:** accepted

## Context

Tasks must survive a restart, so #59 stores them in PostgreSQL behind the
existing `TaskRepository` (ADR-003). Two things make this harder than
annotating the Domain classes. First, `Task` enforces every rule as it is
built and changed: its constructor adds the six checks and a `TASK_CREATED`
audit entry, and each change adds more entries. Loading a stored task through
those paths would run rules again and add audit entries that never happened.
Second, audit history is append-only (README Rule 9), and so are artifact
versions and test runs, so the database must never see an UPDATE or DELETE
for those rows, even though the rest of a task changes freely.

## Decision

The Domain stays plain Java with no JPA annotations. Each Domain class gets a
public static `restore(...)` factory that sets the stored values directly,
including ids and timestamps. It checks only the shape of the data (for
example, exactly one check of each type) and applies no workflow rule and adds
no audit entry. Timestamps are cut to microseconds when they are created,
the precision PostgreSQL stores, so a reloaded task is equal in every field.

In `verifai.data`, JPA entities mirror the aggregate and `TaskMapper`
converts both ways. `JpaTaskRepository` loads the stored entity and copies the
task onto it. Requirements, acceptance criteria, checks, and approvals are
element collections that Hibernate updates to match. Artifacts, test runs, and
audit entries are `@Immutable` entities with non-updatable columns, cascaded
with PERSIST only, and the mapper only appends the ones past the stored count.
Before saving, the mapper checks that the stored history is the start of the
task's history; if not, another request saved the task in between, and the
save is refused with a 409 instead of silently dropping that change. Flyway
owns the schema (`V1__init.sql`) and Hibernate only validates it. Tests run
the same migration on H2 in PostgreSQL mode.

## Alternatives considered

**JPA annotations on the Domain classes.** Less code, but the Domain would
need no-argument constructors and mutable fields for Hibernate, and the
Domain tier would depend on the persistence framework.

**Package-private restore in `verifai.domain`.** Keeps the factories hidden,
but the mapper would have to live in the Domain package, against the tier
rule that JPA code stays in the Data tier.

**Replace all child rows on every save.** Simplest mapping, but it deletes
and reinserts audit rows, which breaks the append-only rule.

**A database trigger that blocks UPDATE and DELETE on audit rows.** Stronger,
but PostgreSQL-only, so H2 tests would not exercise it. Kept as a follow-up.

## Consequences

Service and presentation code did not change, and loading a task never runs
a rule. The cost is a public `restore` method on each Domain class that the
rest of the app must not call, and a mapper to keep in sync when a field is
added: the round-trip tests compare every field, so a missed field fails
them. Two saves of one task at the same moment still race; the second fails
on the unique audit position and returns a 500. I would add a version column
to `Task` if that became a real problem.
