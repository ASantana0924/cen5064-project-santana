# ADR-006: Automated test runs are evidence, not verdicts

**Date:** 2026-11-09
**Status:** accepted

## Context

Developers want to record the results of an automated test run (UC-10) next to
the TESTING check. The obvious shortcut is to let the numbers decide the
check: zero failures passes it, any failure fails it. But a green run only
shows that the tests that exist passed. It does not show that they cover the
requirements, and AI-generated tests are often written to pass the code they
came with. The project's promise is that a person verified every check.

## Decision

A `TestRun` belongs to its `Task` and stores the tool, the total, passed, and
failed counts, an optional summary, who recorded it, when, and the artifact
version it ran against. Recording one never changes any check or approval; a
reviewer still marks TESTING passed or failed and may point to a run as
evidence. Runs can be recorded only on an IN_PROGRESS task, each one adds a
`TEST_RESULTS_RECORDED` audit entry, and runs are never edited or deleted.

## Alternatives considered

**Pass or fail TESTING automatically from the counts.** Quicker, but it would
let a green run stand in for human review, so an approval would no longer
mean that a person verified every check (ADR-004).

## Consequences

The TESTING check keeps a person accountable, and the audit history shows
which code each run tested, so a run made against an older artifact is easy
to spot. The cost is one extra step: a reviewer must still mark the check
after a passing run. I would revisit this if runs came straight from CI with
trusted coverage data instead of being typed in by a developer.
