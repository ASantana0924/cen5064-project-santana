# ADR-009: Identify requirements and acceptance criteria by id, not by position

**Date:** 2026-11-16
**Status:** accepted

## Context

Requirements and acceptance criteria were plain strings in a list, and the API
removed one by its 0-based position (`DELETE .../requirements/{index}`). The
midterm peer review (#66) pointed out that positions are not stable: if
someone else removes an item first, every item after it moves up one, and a
removal sent with the old position takes out the wrong item. The frontend
worked around this only inside one browser tab, by disabling every control
while a change saved; two people, or two tabs, could still hit it.

## Decision

Each item is a `TaskItem(UUID id, String text)` in the Domain. `Task` gives a
new item a random UUID when it is added, and the id never changes or is
reused. The routes are `DELETE /api/tasks/{id}/requirements/{requirementId}`
and `.../acceptance-criteria/{criterionId}`, and task details return each item
as `{id, text}`. Removing an id the task does not have, for example one that
was already removed, throws `NoSuchElementException` and returns 404. The
Flyway migration `V2__task_item_ids.sql` adds a `NOT NULL` id column to both
tables and gives every existing row an id.

## Alternatives considered

**A number per task (1, 2, 3, never reused).** Shorter URLs, but the task
would have to store a "next number" counter so a removed number is not handed
out again. A UUID needs nothing stored and matches how tasks are identified.

**Keep positions and refuse a stale removal.** The client would send the text
or a version along with the position. It catches the problem but still names
items in a way that changes under the user.

**A UNIQUE constraint on the id column.** Rows stay keyed by
`(task_id, position)`, and when an item is removed Hibernate moves the later
items up by updating each row in place, so for a moment two rows hold the same
id and the constraint fails. Keying rows by id instead would mean turning
items into entities with their own repository logic. The Domain keeps ids
unique instead: new ids are random, and `Task.restore` refuses a task whose
items share an id.

## Consequences

A removal always removes the item the user chose, or fails with 404 if it is
gone, however many changes happened in between. Two items with the same text
are now separate items. The response shape of `requirements` and
`acceptanceCriteria` changed from strings to objects, so the frontend changed
with it. Audit entries still record the item's text, not its id, so the
history reads the same as before.
