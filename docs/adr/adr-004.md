# ADR-004: Verification and approval rules

**Date:** 2026-10-11
**Status:** accepted

## Context

The project's core promise is that approval means verification actually
happened. The first design had four checks and a single approver, and said
nothing about what happens when code or requirements change after checks
pass. Those gaps would let an approval stand for code nobody verified.

## Decision

Every task has six required checks: REQUIREMENTS, FUNCTIONALITY, TESTING,
ARCHITECTURE, CODE_QUALITY, SECURITY. A task becomes APPROVED only when all six
are PASSED and 2 different developers have approved; the owner may be one of
them. The count is one app-wide setting, `verifai.approvals.required=2`.
A new artifact version, a requirement or acceptance criterion added or removed
on an IN_PROGRESS task, or a reopen resets all checks to PENDING and clears
approvals. An IN_PROGRESS task must keep at least one requirement and one
acceptance criterion, since starting required them. Failing a check clears approvals. An APPROVED task can be reopened
with a required reason. Audit history is append-only.

## Consequences

Approval always refers to the current code and requirements, and the audit
history shows who did what and why. The cost is rework: any change sends the
task back through all six checks. Letting the owner approve keeps a solo
developer plus one reviewer able to finish a task, at the cost of weaker
independence. I would revisit the count or the owner rule if the app were used
by real teams.
