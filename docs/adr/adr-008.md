# ADR-008: Report rule violations with RuleViolationException, and map only it and stale saves to 409

**Date:** 2026-11-16
**Status:** accepted

## Context

`Task` and `Verification` reported broken rules with Java's generic
`IllegalStateException`, and `ApiExceptionHandler` turned every
`IllegalStateException` into a 409 Conflict. The JDK, Spring, Hibernate, and
our own code also throw that exception when something is actually broken, so
a bug could reach the client as a 409 with an internal message, looking like
a normal rule violation and never logged. The midterm peer review (#65)
raised this. `TaskMapper` used the same exception to refuse a stale save,
which is a concurrency conflict, not a Domain rule. In the running app,
Spring's exception translation for `@Repository` beans also wrapped that
exception in `InvalidDataAccessApiUsageException`, so the stale save came back
as a 500, not the 409 that ADR-007 describes.

## Decision

The Domain throws `verifai.domain.RuleViolationException` whenever a workflow
or verification rule blocks an action. It extends `RuntimeException`, not
`IllegalStateException`, so the two cannot be confused. `TaskMapper` refuses a
stale save with Spring's `OptimisticLockingFailureException`. The handler maps
only these two to 409, keeping the same messages. Every other exception that
is not one of Spring's own errors, a plain `IllegalStateException` included,
is logged and returned as a 500 with `Unexpected server error`.

## Alternatives considered

**Subclass `IllegalStateException`.** Existing tests would keep passing, but
a handler for the subclass sits next to code that still catches the parent,
and the line between a rule and a bug gets blurry again.

**Reuse `RuleViolationException` for stale saves.** One fewer handler, but it
puts a Data tier concern into the Domain's exception.

**Custom exceptions for 400 and 404 as well.** `IllegalArgumentException` and
`NoSuchElementException` have the same weakness (a stray `Optional.get()`
would be a 404). Left as a follow-up to keep this change small.

## Consequences

A 409 now always means a rule or a concurrent change, and an unexpected
`IllegalStateException` shows up in the log as a 500 instead of being hidden.
Spring passes `OptimisticLockingFailureException` through its translation
unchanged, so the stale save is a real 409 in the running app, checked by
`StaleSaveTest` with the full application context.
API responses for rule violations did not change, so the frontend did not
either. New Domain rules must throw `RuleViolationException`; one that throws
`IllegalStateException` by mistake returns a 500, which tests catch.
