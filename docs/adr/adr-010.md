# ADR-010: Lock the task row while saving, and load each task from one snapshot

**Date:** 2026-11-20
**Status:** accepted

## Context

ADR-007 refuses a stale save by checking that the stored audit history is the
start of the task's history. The final peer review (#79) found the gap ADR-007
admits. Two saves of one task at the same moment both read the history before
either commits, both pass the check, and both insert an audit entry at the
same position. The second hits the unique constraint and the user gets a 500
instead of the 409. While testing that, I found a worse case. Loading a task
runs several SELECTs, and at READ COMMITTED each one sees the latest commit.
A save that commits partway through a load leaves the loaded copy with the
other developer's audit entry but without their approval. That copy passes
the check, and saving it silently replaces the other approval. Two people
approving at once could both get 200 while only one approval was kept.

## Decision

`JpaTaskRepository.save` loads the stored task with a pessimistic write lock
(`SELECT ... FOR UPDATE`, through `TaskJpaRepository.findForUpdateById`;
Hibernate sends `FOR NO KEY UPDATE` on PostgreSQL, which blocks another save
but not the foreign key checks on new child rows). A second save of the same
task waits until the first commits. Its lists load
lazily after the lock is taken, so they include the first save's rows, and the
existing check refuses it with the 409. `findById` and `findAll` run at
REPEATABLE READ, so every SELECT in a load sees the database as it was at the
first one. Loads take no lock and never wait for a save. Saves keep READ
COMMITTED, because they must see the rows the save before them committed.

## Alternatives considered

**A `@Version` column on `tasks`.** Needs a migration, and when Hibernate
flushes it runs inserts before updates, so the duplicate audit position fails
before the version check and is still a 500. It also does nothing for a load
that mixes two commits.

**Map `DataIntegrityViolationException` to 409.** Fixes the symptom of the
first case only, and turns every constraint bug into a "reload and try
again" message, which ADR-008 rules out.

**SERIALIZABLE for every transaction.** PostgreSQL would refuse one of two
racing saves, but with a serialization error that the API would also have to
map to 409, and it can refuse transactions that did not really conflict.

**A lock in Java (`synchronized` per task id).** Only works while one
instance of the backend runs.

## Consequences

Two saves of one task now run one after the other, and the second always gets
the 409, never a 500 or a lost change. Saves of different tasks lock different
rows and do not wait for each other. A waiting save holds a database
connection, but saves take milliseconds, so I set no lock timeout. The lock
lasts only for the save's own transaction, because services load and save in
separate transactions. `ConcurrentSaveTest` reproduces both races on H2. I
would revisit this if saves became slow, for example with large artifacts.
